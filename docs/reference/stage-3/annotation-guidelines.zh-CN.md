## 1. 问题级标注

每个验证器检出问题（L1 渲染前 / L2 渲染后）在两个独立维度上打分：**严重性** 和 **修复优先级**。两者独立判断，分别记录。

### 1.1 严重性（Severity）

衡量问题对叙事连贯性、一致性、读者理解的**影响程度**。

| 级别 | 标签 | 含义 |
|------|------|------|
| 4 | `blocker`（阻断） | 导致文本根本不可理解、自相矛盾、或因果关系链断裂 |
| 3 | `high`（高） | 明显降低叙事质量，产生显著矛盾 |
| 2 | `medium`（中） | 可察觉但不妨碍理解或阅读流畅性 |
| 1 | `low`（低） | 微小瑕疵、风格问题、边界情况，基本不影响阅读 |

#### 阻断级（blocker）判据

- 已死亡的角色在无复活事件的情况下出现并说话
- POV 角色引用了其不可能知道的信息
- 文本声称"A杀B"而因果模型声明"B杀A"
- 相邻段落对同一核心事实给出矛盾陈述
- 占位值（`changed`/`resolved`）被逐字渲染到正文中
- **判据**：阻断问题总是对应验证器的 error 级别，且问题使因果链不可恢复

#### 高级（high）判据

- 同一角色同一天出现在两个地方且无旅行时间说明
- 角色口吻漂移到与其设定不一致的程度
- 已铺设的伏笔从未回收
- 编造的细节与已建立的世界规则矛盾
- **判据**：典型读者无需仔细分析即能察觉，但文本仍可理解

#### 中级（medium）判据

- 使用了角色注册表之外的别名
- 话语平衡度超过 80% 阈值
- 声明的线索进展在正文中未清楚体现
- 冲突解决类型与正文不匹配
- **判据**：质量敏感的读者能发现，但普通读者可能略过

#### 低级（low）判据

- 单个代词不一致但上下文能消歧
- 非常轻微的节奏偏差
- 重复的冗余描述
- 信息级验证器提示的潜在边界情况
- **判据**：需要仔细重读才能发现的问题

#### 无法判断的处理

1. **缺少上下文**：涉及尚未建立的角色的信息 → 标为 `medium`，备注 `uncertain — insufficient context`
2. **文本模糊**：正文有歧义，两种解读都可能 → 取较严重解读，备注 `ambiguous — pessimistic reading`
3. **工具错误**：标注工具展示数据损坏 → 标记 `cannot_determine`，备注 `tool_error`
4. **语言限制**：若误入英文样本 → 跳过后标 `not_applicable`
5. **干预阈值**：单次标注会话中 >10% 的问题被标记为 `cannot_determine` → 暂停审查

### 1.2 修复优先级（Repair Priority）

衡量**修复该问题的紧迫程度**，独立于严重性。

| 级别 | 标签 | 含义 |
|------|------|------|
| 4 | `blocker`（阻断） | 必须修复才能继续使用或评估该场景 |
| 3 | `high`（高） | 应在下一轮评估或发布前修复 |
| 2 | `medium`（中） | 值得修复但不阻塞进度 |
| 1 | `low`（低） | 可选，仅在涉及同一区域的修改时顺带修复 |

#### 严重性与修复优先级的常见组合

| 严重性 | 修复优先级 | 含义 |
|--------|-----------|------|
| blocker | blocker | 致命失败，必须立即修 |
| high | high | 明显缺陷，应尽快修 |
| high | medium | 严重但修复成本高/难度大 |
| medium | high | 容易修且对质量有明显提升 |
| low | low | 装饰性，可推迟 |

## 2. 场景级质量标注

每个选中场景（单个 NarrativeEvent 的渲染文本）给出**整体质量评分** + 可选理由。

| 级别 | 标签 | 含义 |
|------|------|------|
| 4 | `excellent`（优秀） | 接近完美；可发布的文本，叙事流畅 |
| 3 | `good`（良好） | 有轻微问题的扎实文本；可读且连贯 |
| 2 | `acceptable`（可接受） | 可用但有明显缺陷；叙事意图传达但质量不达标 |
| 1 | `poor`（差） | 显著问题；无法有效传达叙事意图 |

### 判据

- **优秀**：零 blocker、零 high 问题。可能有 0-1 个 low 问题。
- **良好**：零 blocker、零 high 问题。可能有 ≤3 个 medium 或 ≤5 个 low 问题。
- **可接受**：可能有 1 个 high 问题但无 blocker。若有 2+ high 则降为 poor。
- **差**：至少 1 个 blocker 或 2+ 个 high 问题。或文本完全不可读/为空。

## 3. 操作流程

### 步骤 1：拿到标注对象

从项目验证输出（`output/validation.md`）中提取所有 L1/L2 问题列表。标注者需要为每个问题分配两组分数。

### 步骤 2：首轮标注

1. 对每个问题：先判断**严重性**（阅读文本，看问题影响多大）
2. 再判断**修复优先级**（思考修复的紧迫性，独立于严重性）
3. 对每个场景：阅读渲染文本，给出整体**质量评分**
4. 记录格式：
   ```
   问题ID | 验证器 | 严重性 | 修复优先级 | 备注
   scene_id | 质量评分 | 理由
   ```

目标数量：≥120 个问题级标注 + ≥50 个场景级标注（TODO L101）。

### 步骤 3：等待 7-14 天

**必须严格间隔 7-14 天**，否则重测信度无效。

### 步骤 4：盲法复标

1. 系统从首轮标注中按 `min(N, max(50, ceil(0.20*N)))` 抽取复标样本
2. 复标时隐藏首轮分数、随机打乱顺序
3. 完全按照与首轮相同的规则重新打分
4. 记录格式与首轮一致

### 步骤 5：提交数据

将两轮标注数据交给 `npm run bench` 执行统计分析和校准。

## 4. C 能力级别标注注意事项

按 TODO L101，标注需要覆盖每个 validator、每个严重度等级，以及 manifest 声明的 C capability（语义/披露/叙述者等）。

- **S 级能力**（确定性检查）：validator 通过代码直接判定，标注者只需确认 severity 是否合理
- **C 级能力**（语义/披露）：依赖 Pass 2 LLM 分析，标注者需额外判断 LLM 判断本身是否合理

当标注者认为 validator 的判定本身有误（误报或漏报），在备注中记录 `validator_accuracy: false_positive` 或 `validator_accuracy: false_negative`。此元数据用于计算 Pipeline F1。

## 5. 快速参考卡片

```
严重性：
  blocker = 读者完全看不懂
  high    = 读者能看出明显的错
  medium  = 认真看能发现的小问题
  low     = 几乎看不出的瑕疵

修复优先级：
  blocker = 不修不能用
  high    = 下一轮之前必须修
  medium  = 有空就修
  low     = 可选

场景质量：
  excellent = 可以发表
  good      = 扎实但有小问题
  acceptable = 能用但明显有问题
  poor      = 没法用
```
