# 设计哲学

## Novalistically 是什么

Novalistically 是一个**叙事工程系统**。它不是 AI 写作助手，不是聊天机器人封装，也不是带有 LLM 自动补全的文本编辑器。它是一个工程工具，将故事视为结构化数据，通过大语言模型进行渲染，并通过确定性质量保证流水线验证输出。

核心见解很简单：

> **YAML 是真相来源。LLM 是渲染器。验证器是质量检测。**

一切皆源于这种关注点分离。作者以结构化的 YAML 定义来描述角色、事件、规则、关系和叙事约束。LLM 的任务是生成忠实呈现这些定义的散文。验证器的任务是检查散文是否匹配定义——不是通过猜测，而是消费 LLM 自身在第二轮生成的结构化分析 JSON。

## 核心原则

### 1. 输出层面的验证

传统的 AI 写作工具尝试通过设计提示词来控制质量——精心编写指令、添加约束、使用少样本示例。这种方法很脆弱。当模型变更、语言改变或叙事变得复杂时，它就会失效。

Novalistically 采用不同的方法：它验证 LLM 实际生成的内容。但它不是用正则表达式扫描散文。相反，在第二轮 LLM 调用（Pass 2）中，系统要求 LLM 分析自己的输出："你是否包含了这个角色？你是否解决了这个冲突？你使用了什么时态？"LLM 生成**结构化的分析 JSON**——验证器消费的机器可读自检报告。

这种方法语言无关（同一个验证器适用于英语、中文或阿拉伯语散文），语义精确（LLM 能够理解正则表达式无法捕捉的细微差别），且模型无关（任何能输出 JSON 的模型都可使用）。

### 2. 两阶段渲染

每个场景经历两轮 LLM 调用：

- **Pass 1（温度 0.8）：** LLM 根据上下文包撰写纯散文。没有格式约束，没有 JSON 包装——只有引人入胜的叙事文本。

- **Pass 2（温度 0.3，种子 42）：** 散文（来自 Pass 1）和上下文被重新输入 LLM。这次它生成结构化分析 JSON：后置条件覆盖、POV 一致性、发明细节、角色名称使用、叙事检查级别（`exact | similar | absent | contradicted`）、时态检测、冲突分析等。

Pass 2 是**硬性要求**。如果 LLM 未生成有效的分析 JSON，则该渲染被视为失败——没有正则表达式兜底。系统在放弃前会使用 Zod 错误反馈（采用 Instructor 模式）进行重试。

### 3. 带 DAG 因果边的事件溯源

Novalistically 叙事中的每一个状态变更都是一个**事件**。事件按顺序提交，世界状态始终通过从头开始（或从最近的快照）重放事件来推导。

其独特之处在于**时间模型**：事件通过 DAG 边形成因果连接。每个事件定义后置条件（它确立的事实）和前置条件（它依赖的事实）。`ReplayEngine` 从这些因果边构建有向无环图，并按照拓扑顺序重放事件——而非依据 `narrativeOrder`。这保证了因果一致性：倒叙事件的条件基于读者当时已知的信息进行评估，而非事件被创作的时间。

可在配置的间隔创建快照，以防止无限制的重放。

### 4. YAML 作为真相来源

角色、事件、规则、关系、知识边界、线索进展——一切都在 YAML 中定义。散文从来不是定义的一部分；它始终是渲染流水线的**输出**。YAML 定义包括：

- **事件**包含前置条件、后置条件、POV、故事时间、叙述时间、场景类型、线索进展、伏笔、关系影响、规则影响、参与者和受众定位。
- **角色**包含人口学事实、外貌、性格、背景、关系和知识边界。
- **规则**包含如强化、削弱、废除、引入例外等效果。
- **关系**包含状态、方向、情感效价和权力动态。

这种结构化方法使叙事可审计、可测试、可复现。

### 5. 动态分析需求

消费 Pass 2 分析的验证器通过 `getAnalysisRequirements()` 声明它们需要的内容。每个需求指定一个 JSON 字段路径、待检查的属性、schema 示例和 LLM 指令。Pass 2 提示词从这些声明中自动生成——没有硬编码的分析模块。添加新验证器意味着添加新需求；提示词和 schema 会自动更新。

### 6. 事实双重表示

每个 `Fact` 有两种可能的表示形式，且互斥：

- **`value?`** — 用于可通过 `===` 比较的确定性事实。适用于布尔值、枚举和简单字符串。`compareFact()` 返回 `'match' | 'mismatch'`。
- **`narrativeHint?`** — 用于需要 LLM 解释的语义属性。这些被送入 Pass 2 但从不写入 `WorldState`。`compareFact()` 对这些返回 `'deferred'`，表示验证器必须等待分析 JSON。

这种双重表示是确定性验证（适用于简单检查的事项）和语义验证（适用于需要理解的事项）之间的桥梁。

## 为什么不只用提示词工程？

提示词工程是必要的，但不够充分。原因如下：

1. **提示词在不同模型间很脆弱。** 相同的提示词在 GPT-4o、DeepSeek、Claude 和开源模型上产生不同的结果。结构化验证能够捕捉这些差异。

2. **提示词无法捕捉自身的违规。** 如果提示词要求"通篇使用过去时"但模型写了现在时，模型在没有结构化分析的情况下不会自我纠正。

3. **因果一致性需要的不仅仅是提示词。** DAG 和事件溯源在叙事中任意时间点提供关于哪些事实为真的确定性保证。仅靠提示词无法在数百个事件中维持这种一致性。

4. **输出层面的验证是语言无关的。** 为英语编写的验证器适用于中文、西班牙语或斯瓦希里语——只要 LLM 能生成分析 JSON。

## 大图景

Novalistically 将叙事生成视为一个**工程问题**：精确定义输入，通过已知流水线渲染，根据定义验证输出，然后迭代。YAML 定义是规格说明。LLM 是实现。验证器是测试套件。
